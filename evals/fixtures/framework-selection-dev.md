## 覆盖范围

- case-001–003，current_update：当前雇主、住处、称呼的明确更新；旧值仍保留为历史，但当前问题采用新值。
- case-004–006，late_history：较晚记录的旧工作、旧住处与旧乐器，不覆盖较早记录但现实时间更新的当前事实。
- case-007–009，relative_time：相对来源日期解释 yesterday、跨年 tomorrow 和 last month；分别要求日或月精度，不按模型运行日期解释。跨年样例使用 2026-12-31 与 2027-01 的合成时间，特意不依赖机器“今天”。
- case-010–012，same_name：兄弟/同事、牙医/室友、堂表亲/同事中的同名人物具有不同事实，身份关系不能混并。
- case-013–015，negation_hypothetical：不吃某食物、假设搬家与朋友的引语，防止否定丢失、计划当现实及说话主体混淆。
- case-016–018，two_hop：同事→机构→总部、搭档→姓名→宠物、购买物→店铺→地址，答案需要两条来源共同支持。
- case-019–021，abstention：未知生日、用户雇主和猫名；相邻历史中的朋友工作或邻居宠物不能填补缺口。
- case-022–024，chinese：全中文的当前饮品更新、不同月份旅行与明确互动偏好更新，保留中文限定词和事件区分。

## 输入隔离与评分

writer 只能读取 `history` 的中性来源编号、来源观察时间和正文；reader 只能接收相同的正常问题/查询时间及该 profile 实际召回的上下文。`category`、`gold`、rationale、预期证据、答案别名及题型提示均属于评分侧，不得进入 writer、检索规划或 reader。数据本身包含这些独立字段，具体 runner 仍须以白名单接口和测试落实隔离；文件格式本身不构成“已验证无泄漏”的结论。

统一 reader 返回 `{"answer": "简短答案或 null", "source_ids": ["s001"]}`。answer 为 null 是明确拒答；历史不存在依据时不能用常识补齐个人事实。别名只接受文件中事先列出的等价值，不对结果临时放宽匹配。日期输出要求 YYYY-MM-DD，月份输出要求 YYYY-MM，避免把月份伪造成某一天。大小写和空白等规范化规则应在运行前固定并记录。

`gold.evidence_sources` 记录最小必要支持集合，不是“返回多一条相关来源就错误”的排他名单；尤其两跳问题要保留两条真实来源。应分别报告回答正确、必要证据覆盖、引用是否合法及有无多余引用。相对时间答案可能由观察时间和短语确定，并非正文逐字字符串，不能用“答案是否逐字出现在正文”代替正确性判断。

## 核对与限制

已逐条核对答案、叙述主体、来源集合和日期锚点。程序性检查也确认 24 个中性连续 case ID、8 类各 3 条、来源编号不重复、全部引用存在、历史时间不晚于问题时间，以及 3 条拒答 answer=null/aliases=[]。该检查不调用模型，不提供质量成绩。

短历史上的原文基线很强是预期结果，不据此压低原文预算或移除不利于框架的样例。三个 profile 必须使用同一历史和 reader 条件，写入/检索成本分别报告。精确答案失败需要保存原预测并分类；裁判复核只作为诊断，不能挑最好的一次替换原分数。
